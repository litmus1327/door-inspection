Review flags — where the code may not match intent

Found while tracing the logic for this map. Each is worth a look before trusting the checklist output.

1
Dead stair-door check. getApplicableItems L183 tests swing === 'stair', but swing is only ever single / dbl_pair / dbl_dual_egress / dbl_active / dbl_inactive — the condition can never fire. The real 60-min stair override lives in the auto-flag effect (L1047, L1065) via isStairDoor, which is never passed into getApplicableItems. Net effect: a 45-min door on a 1-hr fire barrier stair gets auto-flagged deficient, but the rating_door row itself is not shown in the checklist (45 ≥ 45, so doorIsUnderrated is false).
2
Same bug class for corridor doors. The 1-hr partition corridor override (L1103: 20-min door + isCorridorDoor → deficient) also only exists in the auto-flag effect. getApplicableItems never sees isCorridorDoor, so the flagged rating_door row is hidden there too.
3
Unreachable branches x5, x9, x10. Fully implemented in getBranchResult (damaged astragal, damaged sweep, bottom rod/flush bolt) but no checklist item carries branch: 'x5' / 'x9' / 'x10'. The likely intended hosts — pi_astragal (L282) and pi_sweep (L283) — have no branch at all, so those follow-up question chains can never be asked.
4
Three different “illegitimate mag-lock” definitions. Blocking prompt (L161): mag && !motion && !PTE. Item show (L314): mag && (!motion || !PTE). Auto-flag (L1127): mag && (motion XOR PTE). These disagree when exactly one of motion sensor / PUSH-TO-EXIT is present. Decide which is canonical.
5
Docs drifted from code. DEVELOPMENT_NOTES.md (and CLAUDE.md) say the stair override keys off hwState.hw_stair_door — no such hardware var exists in HARDWARE_VARS. The code uses the isStairDoor setup question instead.
